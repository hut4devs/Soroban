# ADR-0001: Anchor approved Hut4Devs commitments on Stellar as verifiable hashes

- Status: Proposed (awaiting review; no contract implementation may begin until this ADR is approved)
- Date: 2026-10-11
- Deciders: Hut4Devs maintainers
- Links: issue #2, [docs/ARCHITECTURE.md](../ARCHITECTURE.md), [docs/DATA_BOUNDARIES.md](../DATA_BOUNDARIES.md)

## Context

Hut4Devs records approval decisions off-chain (for example, an approved
membership application or an approved accommodation request). Today a member or
partner has no way to verify that a record they were shown was also the record
the backend committed to at the time of approval: verification requires trusting
the backend's own storage, and there is no independent point-in-time evidence.

This repository exists to evaluate whether Stellar/Soroban genuinely improves
Hut4Devs. The README requires a concrete problem, explicit non-goals, and
testnet-first execution before any contract is written.

## Decision

We will evaluate one narrowly scoped use case, the **Trust Trail**: the backend
anchors a SHA-256 hash commitment of each *approved* decision on Stellar
Testnet, so that the existence and integrity of that approval can later be
verified by anyone without trusting the backend's storage.

Scope of the contract (when implemented, after this ADR is approved):

- Input: a 32-byte commitment hash plus an opaque commitment id, authorized by
  the configured backend anchorer account.
- State: `commitment_id -> hash`, the anchorer authority, and the anchoring
  ledger sequence. Nothing else.
- Output/event: one anchor event per commitment for RPC-based verification.
- The commitment preimage is defined in
  [docs/DATA_BOUNDARIES.md](../DATA_BOUNDARIES.md); it contains no personal,
  accommodation, or payment data.

### Measurable benefit

- **Tamper evidence:** any alteration of an approved record's canonical inputs
  changes its SHA-256 commitment, so verification against the on-chain hash
  fails. Undetected silent alteration requires a SHA-256 collision
  (negligible, <= 2^-128).
- **Verification without backend cooperation:** the stored hash is readable
  through public Soroban RPC with no API key, account, or backend availability.
- **Bounded cost:** at most one contract invocation and 32 bytes of contract
  storage per approval; no per-member or per-booking state.

### Alternatives considered

1. **Full on-chain booking or membership records.** Rejected: it publishes
   personal and accommodation data on a public ledger, violating the project's
   data-boundary principles.
2. **Off-chain-only signed hash chain (backend audit log).** Viable and kept as
   a non-blocking option (see below), but it cannot provide verification that
   does not ultimately rely on the backend.
3. **Anchoring on a non-Stellar chain.** Rejected for scope: this repository
   evaluates Stellar, and Stellar's fixed low fees are sufficient for the
   bounded cost target.

### Non-blocking off-chain option

The backend signed hash-chain audit log (alternative 2) can be built and shipped
independently of any chain. Product correctness does not depend on chain
inclusion: per the README, an on-chain event is never treated as proof that an
off-chain claim is true. If the anchor is rejected, delayed, or unavailable,
approvals continue to work off-chain and the audit log remains the primary
record; anchoring is an optional integrity enhancement layered on top.

### Assumptions

- The backend authorizes approvals; the contract only checks that the
  configured anchorer authorized an anchor. It never decides who may approve.
- All work happens on Stellar Testnet first. Mainnet requires a separate,
  explicit production-readiness decision.
- Commitment ids are generated by the backend from a CSPRNG and are not derived
  from member or booking data.

## What remains off-chain (normative)

Member identity and any PII, membership and accommodation records and
documents, payment-provider payloads, the mapping from commitment id to member
or booking, and all approval workflow/permissions stay off-chain. The backend
remains authoritative for off-chain truth and permissions. The full rules and
the commitment canonicalization format are specified in
[docs/DATA_BOUNDARIES.md](../DATA_BOUNDARIES.md).

## Invariants to encode before implementation

Per CONTRIBUTING.md, these invariants must be encoded in tests before business
logic grows:

- The contract stores only 32-byte hashes, opaque ids, the anchorer authority,
  and ledger-derived values; it never accepts or stores raw document, identity,
  or payment data.
- Only the configured anchorer may anchor or rotate authority; all other
  callers are rejected.
- Anchoring the same id twice with a different hash is rejected.

## Consequences

- `docs/DATA_BOUNDARIES.md` becomes normative for what may touch the chain.
- The trust-trail contract stays a scaffold until this ADR is reviewed and
  approved; review happens before implementation, not after.
- Future ADRs cover upgradeability, key custody, and a mainnet decision, none of
  which are settled here.
